# 百日临高 v0.2：九大机制扩展规划

## Summary（目标）

在现有纯静态原型基础上，引入 9 个借鉴《王权》的机制（编号沿用讨论：**1、2、4、5、6、7、8、9、10**），并先把项目从单文件 IIFE 重构为 **ES 模块结构（无构建）**，数据层**按机制拆分为多个模块**。整体分两大阶段：先重构打地基，再按依赖顺序一个一个加机制，每加一个都用 `tools/balance_check.py` 回归验证。

九大机制：
- **1 零和约束**：每个选项收益必须由另一维下降/风声上升/耗天数支付（治当前"四柱走高"病）。
- **2 角色回归**：元老/部门作为反复登场角色，记忆玩家偏袒，长期偏爱某维会招致反噬。
- **4 解锁/资产**：完成关键决策解锁新卡组与规则改变（如建成码头解锁贸易卡链）。
- **5 任务/隐藏目标**：每阶段一个隐藏 KPI，达成给增益、失败埋隐患。
- **6 组合隐藏卡**：多前置条件满足后触发稀有事件（升级现有 followups）。
- **7 决斗小游戏**：海战/反围剿做成轻量子玩法（限时连续卡），打断划卡单调。
- **8 风声神秘化**：风声改为"神秘条"，只用文本暗示，精确模式下也不给准数。
- **9 阶段卡池演化**：同一事件在不同阶段有不同后果（戒严在登陆期 vs 稳定期）。
- **10 结局图鉴**：跨周目收集结局、解锁开场变体，驱动重玩。

## Current State Analysis（现状，基于实际阅读）

- **无构建纯静态项目**。`web/index.html` 末尾两个顺序 `<script>` 加载 `src/data.js` 与 `src/app.js`。
- `web/src/data.js`（约 352 行）：一个 IIFE，用工厂函数 `c()`/`e()` 定义全部数据，挂到 `window.GAME_DATA`。含 `stats / initialState / stages / reports / endings / successEndings / crisisCards / cards`。
- `web/src/app.js`（约 577 行）：一个 IIFE，全部逻辑揉在一起——`els` DOM 引用、`state`、`makeInitialState`、抽卡调度 `drawNextCard`、结算 `applyChoice`、一系列 `render*`、`save/load`、事件绑定与指针拖拽。
- `tools/balance_check.py`：用正则解析 `data.js` 的 `c()/e()` 定义，做静态 lint + 蒙特卡洛模拟。**依赖当前 data.js 的文本格式**，重构数据文件后必须同步更新其解析逻辑。
- 关键约束：现状"双击 index.html 即可运行"。改用 `<script type="module">` 后，`file://` 协议会因 CORS 阻止模块加载，**必须通过本地静态服务器访问**（如 `python -m http.server`）。用户已知悉并接受此代价。

## 重构后的项目结构（Phase 0 目标）

```
web/
├── index.html                  # 改为 <script type="module" src="./src/main.js">
├── styles.css
├── README.md                   # 更新运行说明：需本地静态服务器
└── src/
    ├── main.js                 # 入口：装配 engine + UI，boot()
    ├── core/
    │   ├── state.js            # 初始状态、clamp、状态读写
    │   ├── engine.js           # 抽卡调度 drawNextCard、结算 applyChoice
    │   └── storage.js          # save/load（localStorage）
    ├── systems/                # 每个机制一个系统模块（按需逐步新增）
    │   ├── crisis.js           # 危机/风声触发（从 engine 抽出）
    │   ├── characters.js       # #2 角色回归
    │   ├── quests.js           # #5 任务目标
    │   ├── unlocks.js          # #4 解锁/资产
    │   ├── combos.js           # #6 组合隐藏卡
    │   ├── duel.js             # #7 决斗小游戏
    │   └── endingpicker.js     # 结局判定（从 engine 抽出）
    ├── ui/
    │   ├── dom.js              # 集中 DOM 引用
    │   ├── render.js           # render / renderMetrics / renderCard ...
    │   ├── wind.js             # #8 风声神秘化渲染
    │   ├── input.js            # 键盘/指针/按钮绑定
    │   ├── modal.js            # 弹窗、说明
    │   └── gallery.js          # #10 结局图鉴 UI
    └── data/                   # 数据按机制拆分
        ├── index.js            # 汇总导出，组装等价于旧 GAME_DATA 的对象
        ├── factory.js          # c()/e() 工厂函数（供各数据模块复用）
        ├── stats.js            # 四柱定义、initialState
        ├── stages.js           # stages、reports
        ├── cards.js            # 主卡池（landing/foothold/build/stable/SP/SER）
        ├── crisisCards.js      # 危机/风声卡
        ├── characters.js       # #2 角色定义与诉求
        ├── quests.js           # #5 阶段隐藏目标
        ├── unlocks.js          # #4 解锁条件→卡组/规则
        ├── combos.js           # #6 组合触发定义
        ├── duels.js            # #7 决斗关卡数据
        └── endings.js          # endings、successEndings、图鉴元数据
```

设计要点：
- 数据模块只导出纯数据 + `factory.js` 的工厂函数，`data/index.js` 聚合成一个 `GAME_DATA`（保持 engine 侧最小改动）。
- 各 `systems/*` 模块导出纯函数（输入 `state`、输出决策/卡），engine 编排它们，避免相互直接依赖。
- 为兼容 `balance_check.py`：保持 `cards.js`/`crisisCards.js` 内 `c()/e()` 写法不变，仅调整脚本让它读 `data/` 目录下多个文件（glob 合并后再正则解析）。

## Proposed Changes（分阶段落地，一个一个加）

排序原则：先地基（Phase 0），再"改造存量"的低风险机制，最后"增量玩法"的大机制。每个机制完成后运行 `python tools/balance_check.py` 回归。

### Phase 0：ES 模块化重构（无行为变化）
- 拆分 `app.js`/`data.js` 为上述结构；`index.html` 改 `type="module"`。
- 更新 `README.md` 运行方式；更新 `balance_check.py` 使其扫描 `web/src/data/*.js`。
- **验证**：本地起服务器，完整玩一局，行为与重构前一致；`balance_check.py` 输出与重构前数字一致（+264.5 / 模拟分布不变）。

### 机制 1 — 零和约束（数据治理，先做）
- 在 `factory.js` 或 `balance_check.py` 落地规则：非危机卡每选项 `Σ四柱 ≤ 0.6×风声↑ + 天数 + 2`；两侧需存在符号相反维度。
- 按 balance 报告优先级修卡：先 12 张无对冲卡，再超额 >8 的通胀卡。
- **验证**：全池两侧四柱净值均值总和从 +264.5 收敛到 |值|<40；模拟中 random 玩家四柱中位回落到 40~60，军务/生计 P90 不再顶 100。

### 机制 8 — 风声神秘化（纯 UI，低风险）
- 新增 `ui/wind.js`：风声只显示神秘条 + 文本暗示，移除精确括号数值（即使精确模式也仅给模糊档位）。
- **验证**：UI 不再出现风声精确数字；四柱精确模式不受影响。

### 机制 9 — 阶段卡池演化（改造抽卡）
- 卡牌 effects 支持"按阶段覆盖"：`stageEffects: { landing:{...}, stable:{...} }`，engine 结算时优先取当前阶段变体。
- 挑选代表性事件（如戒严、征粮）配置阶段差异。
- **验证**：同一卡在不同阶段结算数值不同；balance_check 支持阶段变体统计。

### 机制 2 — 角色回归（新系统）
- `data/characters.js`：定义角色（吴南海/邬德/王洛宾/保卫组等），字段含 `favorStat`（其主张的维度）、`backlashCard`（坐大反噬卡）。
- `systems/characters.js`：记录 `state.favor[char]`，某角色被长期偏袒（favor 超阈值）时向 `pending` 注入其反噬卡；卡牌可标注 `source` 关联角色。
- **验证**：连续偏袒某维 → 触发对应反噬卡；模拟中"堆单维"策略被自然惩罚。

### 机制 5 — 任务/隐藏目标（新系统）
- `data/quests.js`：每阶段一个隐藏 KPI（如登陆期"生计不低于 40"）。
- `systems/quests.js`：阶段切换时结算上一阶段 KPI，达成给增益卡/解锁，失败注入隐患卡。
- **验证**：达成/失败分别产生可见后果；不破坏零和大盘。

### 机制 4 — 解锁/资产（新系统）
- `data/unlocks.js`：`条件 → 解锁卡组/规则`（如建成浮动码头→贸易卡链、办成教导队→新军卡链）。
- `systems/unlocks.js`：维护 `state.unlocked[]`，`engine.availableCards` 按解锁过滤/加权。
- **验证**：未解锁的卡组不入池；达成解锁后新卡可抽到。

### 机制 6 — 组合隐藏卡（升级 followups）
- `data/combos.js`：多前置条件（历史选择集合）→ 稀有事件（如低调处理广州+黎区+苟家庄→隐秘扩张隐藏结局线）。
- `systems/combos.js`：在结算后检查组合是否满足，满足则解锁隐藏卡/结局。
- **验证**：满足组合触发隐藏卡；未满足不触发。

### 机制 10 — 结局图鉴（跨周目持久化）
- `data/endings.js` 增图鉴元数据；`ui/gallery.js` + `storage.js` 用独立 localStorage key 记录已解锁结局。
- 达成新结局写入图鉴；可选开场变体解锁。
- **验证**：结局后图鉴新增条目；跨周目保留。

### 机制 7 — 决斗小游戏（最大，最后）
- `data/duels.js` + `systems/duel.js` + `ui`：把海战/反围剿做成限时连续卡的攻防子流程，结果回写四柱。
- engine 在特定卡触发时进入 duel 模式，结束后回到主循环。
- **验证**：触发决斗→子玩法可完整进行→结果正确结算回主局。

## Assumptions & Decisions（假设与决策）

- **A1**：采用原生 ES 模块，不引入 Vite/打包器；代价是运行需本地静态服务器（`python -m http.server` 于 `web/` 目录）。已与用户确认接受。
- **A2**：数据按机制拆分为多个 `data/*.js` 模块，`data/index.js` 聚合，保持 engine 侧接口接近旧 `GAME_DATA`，降低迁移风险。
- **A3**：`balance_check.py` 保留正则解析路线，改为扫描 `data/` 多文件，不改工具技术栈。
- **A4**：机制落地顺序 = Phase0 → 1 → 8 → 9 → 2 → 5 → 4 → 6 → 10 → 7，每步独立可交付、独立回归。
- **A5**：风声机制 8 移除精确数字与设计文档 5.1「玩家不应总能精确知道风声」一致。
- **D1（待定）**：机制 7 决斗的具体交互形态（限时点击 / 卡组对抗 / 骰子判定）在进入该阶段前再细化，不阻塞前面机制。

## Verification（总体验证策略）

1. 每个阶段完成后：本地起服务器手动通关一局，确认无控制台报错、流程闭合。
2. 每次改数据/加机制后运行 `python tools/balance_check.py`，盯两个指标：全池四柱净值均值总和趋近 0、模拟四柱中位趋近 50。
3. Phase 0 重构以"行为与数字零变化"为通过标准（纯结构变更）。
4. 存档兼容：`storage.js` 增加版本号，跨机制升级时旧存档可降级或提示重开。
