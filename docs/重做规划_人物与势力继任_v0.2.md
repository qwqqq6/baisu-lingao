# 《临高启明同人游戏》重做规划：人物与势力继任 v0.2

## 1. 重做方向

游戏从“固定 100 天的执委会裁断”改为“人物执政、势力扩张、权力继任”的长期卡牌决策游戏。玩家开局选择一名小说人物并扮演其本人；人物有性格、路线、专属卡牌和专属选项。执政过度偏激或局势失衡时，人物可能被罢免、刺杀、架空、问责或病退，随后由局势自动推举下一任掌权者，游戏继续推进。

游戏不再设置固定 100 天目标。时间仍以“天”为单位推进，但主要压力来自势力越来越多、旧矛盾沉淀、新组织进入候选池、部分旧事件退出卡池，以及继任者必须处理前任遗留问题。

## 2. 首发人物

首发提供五名可选人物，每人代表一条路线。

| 人物 | 路线 | 定位 | 新手友好度 |
| --- | --- | --- | --- |
| 吴南海 | 农政/民生 | 粮食、农庄、归化民安置、地方生产共同体 | 较高 |
| 邬德 | 民政/组织 | 俘虏治理、工分制度、基层组织、归化民网络 | 中 |
| 北炜 | 军务/安全 | 侦察、警戒、反击、治安、外部威胁 | 较低 |
| 马千瞩 | 计划/工业 | 计划委员会、工业优先级、资源调度、长期建设 | 较低 |
| 文德嗣 | 执委会/裁断 | 元老院平衡、会议压制、合法性、危机背锅 | 较高 |

人物不是皮肤，而是执政方式。选择界面应展示姓名、路线、性格关键词、擅长领域、天然风险、初始加成和可能倒台方式。

## 3. 人物能力与缺陷

每名人物都有主动能力，也有性格缺陷。主动能力可以帮助玩家处理路线内问题，但会强化对应风险。

示例方向：

- 吴南海能缓和生计危机，但会提高南海农庄或农政系统影响力。
- 邬德能缓和民望和俘虏治理问题，但会扩大基层组织网络。
- 北炜能压制军务危机，但会提高风声、敌意和刺杀风险。
- 马千瞩能提升长期项目收益，但会牺牲短期民望或激化资源争夺。
- 文德嗣能否决一次元老院反噬或会议危机，但会积累个人压力。

缺陷必须存在，避免人物成为单纯数值加成。

## 4. 继任与下台

人物下台不是整局失败。下台后，系统根据当前局势自动推举继任者。

继任不应把具体人物逻辑写死在程序里。程序只负责读取候选、判断条件、计算权重和抽取结果；谁在什么局势下适合继任，应写在人物卡或人物数据中。

继任权重由人物卡声明：

- 当前强势势力是否支持该人物。
- 当前危机类型是否需要该人物路线。
- 前任倒台原因是否排斥该人物路线。
- 人物是否死亡、流放、被清洗或暂时不可用。
- 当前合法性局势是否需要该人物背书。

人物下台分为个人结局和政局后果。罢免、架空、刺杀、病退、问责等应有不同影响。非死亡下台的人物可以继续作为反对派、派系领袖、会议对手或潜在继任者存在；死亡或彻底退场则留下遗产、清算或殉难类卡牌。

部分倒台方式与人物路线绑定：

| 人物 | 更易触发的倒台 |
| --- | --- |
| 吴南海 | 问责、架空、农庄坐大 |
| 邬德 | 罢免、清洗、基层网络失控 |
| 北炜 | 刺杀、军变、强硬派反噬 |
| 马千瞩 | 问责、计划失败、工业事故 |
| 文德嗣 | 架空、会议夺权、合法性崩塌 |

### 4.1 人物压力模型

每个执政人物都有隐藏压力。压力不直接显示数值，只通过卡牌措辞、会议风向、人物来信、阶段报告和倒台前兆暗示。

基础压力包括：

| 压力 | 含义 | 可能后果 |
| --- | --- | --- |
| `personal_pressure` | 个人执政压力、背锅、疲劳和问责积累 | 病退、问责、崩溃 |
| `faction_alarm` | 其他派系对当前执政者的警惕 | 架空、罢免、会议夺权 |
| `violence_risk` | 暴力风险、刺杀、兵变、清洗反噬 | 刺杀、军变、流血清算 |
| `legitimacy` | 继任合法性和被承认程度 | 继任危机、会议夺权、执政失效 |

`legitimacy` 与其他压力不同，越低越危险；其他三项越高越危险。

不同人物有不同敏感点：

| 人物 | 主要压力来源 |
| --- | --- |
| 吴南海 | 农庄坐大、农政系统自治、元老院警惕 |
| 邬德 | 基层网络扩张、私人组织嫌疑、归化民依赖 |
| 北炜 | 军务化、强硬镇压、外部仇恨、暴力反噬 |
| 马千瞩 | 计划债务、项目事故、工业优先挤压民生 |
| 文德嗣 | 会议压力、背锅压力、合法性消耗、各派拖拽 |

人物倒台不是单一阈值触发。系统应综合判断压力、四柱、隐藏势力和当前事件：

- 压力接近危险区时，提高倒台前兆卡权重。
- 压力进入危险区且局势恶化时，触发倒台卡。
- 如果仍有强势支持者，可能从“罢免”变成“架空”或“勉强续任”。
- 如果暴力风险过高，温和倒台可能升级为刺杀、兵变或清洗。

人物压力属于运行时状态，但不放入公开 UI。它可以写入存档，也可以被选项效果、势力索价、继任事件和前任遗产修改。

### 4.2 倒台判定

倒台不是某个数值爆表后的固定结局，而是由人物压力、四柱、隐藏势力、当前系列和前任遗产共同决定。

基础判定方向：

| 主要危险 | 辅助局势 | 倒台倾向 |
| --- | --- | --- |
| `personal_pressure` 高 | 生计恶化、元老院不满、项目失败 | 问责、病退、崩溃 |
| `faction_alarm` 高 | 元老院强、专业系统坐大、会议系列活跃 | 罢免、架空、会议夺权 |
| `violence_risk` 高 | 军务化、外部敌意、强硬镇压、保卫系统过强 | 刺杀、兵变、流血清算 |
| `legitimacy` 低 | 继任支持不足、前任遗产沉重、元老院分裂 | 继任危机、执政失效 |

如果当前人物仍有强势支持者，倒台可能被推迟或转化：

- 农庄、基层、保卫、计划委员会等势力强烈支持时，人物可能“强行续任”。
- 强行续任会提高相关势力影响力，也会提高其他派系警惕。
- 强行续任后，下一轮倒台风险更高，且后续继任者更容易抽到擦屁股卡。

倒台前应优先出现前兆卡，而不是突然结束人物任期。前兆卡可以给玩家一次补救机会，但补救本身也有代价。

示例：

- 吴南海农庄影响力过高，先出现“农庄调度质询”前兆卡；处理失败后进入架空或问责。
- 北炜强硬镇压过多，先出现“营地外的黑名单”前兆卡；继续强硬可能升级为刺杀。
- 马千瞩计划债务累积，先出现“项目排期无法兑现”前兆卡；若生计继续恶化，触发计划问责。
- 文德嗣合法性过低，先出现“扩大会议重新授权”前兆卡；若元老院继续分裂，触发会议夺权。

### 4.3 数据驱动继任

继任应通过人物卡/人物数据驱动，而不是在程序里写固定规则。程序只提供通用流程：

1. 读取所有人物的继任定义。
2. 排除不可用人物。
3. 判断每个候选人的 `requires`、`excludes` 和权重修正。
4. 按权重抽取或选择继任者。
5. 展示对应继任卡。

人物继任定义示例：

```json
{
  "id": "wunanhai",
  "name": "吴南海",
  "route": "农政/民生",
  "succession": {
    "baseWeight": 8,
    "requires": [
      { "state": "character.wunanhai.available", "equals": true }
    ],
    "excludes": [
      { "state": "character.wunanhai.dead", "equals": true }
    ],
    "weightModifiers": [
      {
        "when": [
          { "stat": "livelihood", "lte": 30 }
        ],
        "add": 8,
        "reason": "生计危机时，农政路线更容易被推上台。"
      },
      {
        "when": [
          { "force": "farm", "metric": "influence", "gte": 15 }
        ],
        "add": 6,
        "reason": "南海农庄坐大后会支持吴南海复出或继任。"
      },
      {
        "when": [
          { "state": "fall_reason.farm_overreach", "equals": true }
        ],
        "add": -10,
        "reason": "前任刚因农庄坐大倒台时，农政人物短期受排斥。"
      }
    ],
    "entryCard": "CHAR-WNH-SUCC-001"
  }
}
```

继任卡负责讲清楚“为什么是这个人上台”，并写入初始后果：

```json
{
  "id": "CHAR-WNH-SUCC-001",
  "series": "politics.succession",
  "type": "succession",
  "title": "农政派被推到台前",
  "source": { "kind": "force", "id": "council", "name": "扩大会议" },
  "text": "粮食和安置问题压过了会议上的争吵。吴南海被推到台前，所有人都希望他先把锅里的饭稳住。",
  "options": {
    "left": {
      "label": "接受临时授权",
      "effects": {
        "ruler": "wunanhai",
        "personal": { "legitimacy": 5, "faction_alarm": 2 },
        "states": [
          { "id": "ruler.current", "op": "set", "value": "wunanhai" }
        ]
      }
    },
    "right": {
      "label": "要求扩大农政权限",
      "effects": {
        "ruler": "wunanhai",
        "personal": { "legitimacy": 8, "faction_alarm": 5 },
        "forces": {
          "farm": { "influence": 4, "satisfaction": 4 }
        },
        "states": [
          { "id": "ruler.current", "op": "set", "value": "wunanhai" }
        ]
      }
    }
  }
}
```

这样后续新增人物时，只需要新增人物定义和继任卡，不需要修改继任算法本身。

## 5. 势力系统

势力通过事件解锁，开局不全部出现。初始只存在元老院和临时权力中枢。随着卡牌推进，接触本地人会引出本地土著/村社，建立南海农庄会引出农庄系统，成立东门市会引出商贸网络。

势力数值全部隐藏，不提供势力面板。玩家只能通过卡牌、来源、传闻、阶段报告和人物发言判断局势。

每个势力至少有三项隐藏数值：

| 数值 | 含义 |
| --- | --- |
| 影响力 | 该势力能否左右政局和继任 |
| 满意度 | 该势力是否支持当前执政者 |
| 敌意/警惕 | 该势力是否准备反抗、拆台或夺权 |

原四柱指标保留原样：元老院、民望、军务、生计仍是整体局势指标，风声仍是隐藏外部压力。势力数值描述具体群体，不替代四柱。

## 6. 势力收益与索价

势力不是单纯威胁。每个势力强大后都能提供收益，也会提出索价。

示例：

- 南海农庄能稳定粮食，但要求更多自治和资源。
- 保卫系统能压制危机，但要求扩大权限。
- 计划委员会能提升项目效率，但会挤压地方样板和短期民望。
- 商贸网络能带来物资和情报，但会增加风声和技术泄密风险。

势力冲突主要通过卡牌表现，不在面板中直接显示关系。

## 7. 卡牌系统重做

卡牌分为公用卡和人物相关卡。公用卡仍保持左右二选一，但在特定人物执政时，其中一个选项可能被替换为人物专属版本；某些人物也可以看到额外提示，但不一定增加新选项。

专属选项不是纯加强，而是更符合人物性格。它可能更有效，也可能更危险。

人物相关卡分为：

- 开局卡：体现人物上台后的第一件事。
- 性格卡：周期性考验人物路线。
- 反噬卡：路线过度后出现。
- 倒台卡：触发罢免、刺杀、架空、问责等。
- 遗产卡：人物下台后，其制度、旧部或反对派继续影响局势。
- 擦屁股卡：继任者处理前任留下的烂账。

人物专属选项通过标签概率触发。卡牌有标签，例如 `农庄`、`军务`、`俘虏`、`会议`、`工业`；人物也有标签。标签相交时，专属选项有概率出现，而不是必定出现。

## 8. 卡牌来源与抽取优先级

来自人物或组织直接提出的卡牌必须保留来源显示，例如“吴南海”“保卫组”“计划委员会”“值班秘书”。由于势力数值隐藏，来源是玩家判断局势的重要线索。

新版抽卡优先级：

1. 继任/倒台卡
2. 未处理插入卡
3. 致命危机卡
4. 人物反噬卡
5. 势力索价卡
6. 阶段/事件关键卡
7. 人物专属卡
8. 公用日常卡

重大行动卡继续保留多天消耗，用于表现道路、农庄、工业、军工、外贸等长期项目。

## 9. 卡池演化

卡池随时间、事件、人物和势力变化而演化。新势力出现后，其相关卡牌加入候选池；旧阶段、已解决矛盾或失去条件的卡牌可以被剔除。

示例：

- 未接触本地人前，不出现本地村社相关卡。
- 建立南海农庄后，农庄索价、农庄扩张、农庄坐大类卡加入。
- 东门市成立后，商贸、治安、泄密和市场投机类卡加入。
- 某人物下台后，其开局卡退出，但遗产卡和擦屁股卡加入。

## 10. 多维卡池结构

卡牌不能按“人物 x 事件 x 势力”写成大量重复卡，而应采用分层结构：一张基础事件卡承载通用冲突，再由人物、势力、阶段和历史状态挂载变体。

### 10.1 卡牌分层

| 层级 | 作用 | 示例 |
| --- | --- | --- |
| 基础卡 | 定义事件主题、来源、默认左右选项 | “南海示范农庄” |
| 人物变体 | 替换某一侧选项或追加提示 | 吴南海可选“办成归化民样板” |
| 势力变体 | 根据隐藏势力状态改变文本、代价或后续 | 农庄影响力过高时追加索价 |
| 阶段变体 | 同一事件在不同时期有不同强度 | 登陆期重生计，扩张期重自治 |
| 历史变体 | 根据前置选择、前任遗产、已解锁事件调整 | 前任留下烂账时出现擦屁股版本 |

基础卡必须能独立运行；所有变体都是可选覆盖层。

### 10.2 卡牌字段建议

每张基础卡建议包含：

- `id`：唯一编号。
- `pool`：所属卡池，如 `landing`、`farm`、`security`、`trade`。
- `type`：日常、关键、危机、势力索价、人物反噬、倒台、遗产。
- `source`：提出该事件的人物或组织。
- `tags`：用于匹配人物、势力和事件条件。
- `requires`：出现条件，例如已接触本地人、已建立南海农庄。
- `excludes`：剔除条件，例如人物死亡、势力瓦解、事件已解决。
- `weight`：基础权重。
- `options`：默认左右两个选项。
- `variants`：人物、势力、阶段、历史状态变体。
- `followups`：后续插入卡或事件标记。

### 10.3 变体规则

人物变体不增加第三选项，而是替换左或右其中一侧，或提供额外提示。替换后的选项不一定更强，只是更符合人物性格。

变体优先级建议为：

1. 致命危机/倒台变体
2. 前任遗产和擦屁股变体
3. 当前执政人物变体
4. 势力状态变体
5. 阶段变体
6. 基础卡默认内容

同一张卡一次只应用最关键的一到两个变体，避免文本和数值过度叠加。

### 10.4 卡池不是目录，而是过滤结果

运行时卡池应由条件动态生成，而不是手写一个固定列表。抽卡流程：

1. 收集所有基础卡。
2. 按 `requires` 和 `excludes` 过滤。
3. 按当前阶段、势力、人物、历史标记调整权重。
4. 按抽卡优先级选择卡牌类型。
5. 应用最匹配的变体。
6. 结算选项、写入状态变化、注入后续卡。

这样可以支持大量人物和事件，同时避免为每个组合写一张新卡。

### 10.5 卡池组织方式

第一版建议按“主题池”组织，而不是按人物组织：

- `core`：登陆、生存、会议、基础四柱。
- `characters`：人物开局、反噬、倒台、遗产。
- `farm`：南海农庄、粮食、农业样板。
- `civil`：俘虏、归化民、工分、基层治理。
- `security`：侦察、警戒、治安、反击。
- `planning`：计划委员会、工业、资源调度。
- `trade`：东门市、外贸、商贸网络。
- `external`：本地村社、官府、海盗、外部风声。

人物只通过标签和变体影响这些主题池，不单独拥有一整套封闭卡池。

### 10.6 卡牌组与系列

卡牌不只按主题池存放，还应归入更细的“组/系列”。主题池解决文件组织，系列解决玩法依赖和剧情推进。

示例：

| 主题池 | 系列 | 说明 |
| --- | --- | --- |
| `farm` | `farm.nanhai` | 南海农庄建立、扩张、自治和反噬 |
| `civil` | `civil.captives` | 俘虏管理、释放、转化和失控 |
| `civil` | `civil.labor` | 工分、劳工政策、分层管理 |
| `security` | `security.guard` | 保卫系统授权、戒严、治安高压 |
| `planning` | `planning.committee` | 计划委员会成立、指标化、计划债务 |
| `trade` | `trade.dongmen` | 东门市、市场、投机、泄密 |
| `external` | `external.locals` | 本地村社、误会、合作和冲突 |

每张卡增加 `series` 字段：

```json
{
  "id": "FARM-001",
  "pool": "farm",
  "series": "farm.nanhai",
  "type": "key"
}
```

系列本身也应有定义，官方内容放在 `game/content/official/series/core.json`：

```json
{
  "id": "farm.nanhai",
  "name": "南海农庄系列",
  "pool": "farm",
  "tags": ["农庄", "农业", "本地人"],
  "requires": [
    { "state": "contact.locals", "equals": true }
  ],
  "unlocks": [
    { "state": "farm.established", "equals": true }
  ],
  "excludes": [
    { "state": "farm.destroyed", "equals": true }
  ],
  "dependsOn": ["external.locals"],
  "entryCards": ["FARM-001"],
  "weight": 10
}
```

系列规则：

- 系列可设置独立 `requires`、`excludes`、`dependsOn` 和基础权重。
- 系列可以依赖另一个系列，例如南海农庄必须先满足本地接触系列。
- 系列可以解锁另一个系列，例如东门市系列可能解锁商贸网络、治安、技术泄密系列。
- 系列可以被关闭或降权，例如本地误会解决后，早期误判卡退出，但后续合作卡仍可保留。
- 卡牌自身条件必须同时满足“系列条件”和“卡牌条件”。
- 系列依赖关系不直接展示给玩家，只通过卡牌来源、文本、阶段报告和后续事件暗示。

运行时抽卡流程应先判断系列是否可用，再从可用系列中抽卡：

1. 收集所有系列定义。
2. 过滤不满足条件的系列。
3. 根据阶段、人物、势力和状态调整系列权重。
4. 在选中的系列内过滤卡牌。
5. 应用卡牌变体并结算。

这样可以表达“某些系列有单独限制”和“某些系列需要满足另一系列要求”，同时避免把所有条件重复写到每张卡上。

### 10.6.1 系列推进规则

系列内部采用“关键节点线性 + 日常/危机分支随机”的结构。

- 关键节点：决定系列方向，通常只出现一次，例如“建立南海农庄”“成立计划委员会”。
- 日常卡：在系列激活后进入候选池，用于表现持续摩擦。
- 危机卡：当四柱、隐藏势力或系列状态恶化时提高权重。
- 索价卡：势力影响力提高后提出要求。
- 后果卡：系列失败、关闭、清算或继任后出现。

每个主要系列都应有进度状态，例如：

```json
{
  "id": "farm.nanhai_progress",
  "type": "level",
  "default": 0,
  "visibility": "hidden",
  "mutability": "reversible",
  "desc": "南海农庄系列进度：0 未开启，1 筹备，2 建立，3 扩张，4 样板化，5 自治坐大。"
}
```

系列可以失败、关闭或转入后果系列。不要把失败简单理解为删除卡池，而是让旧系列退出、新系列接手。

示例：

- `farm.nanhai` 失败或被清算后，关闭农庄扩张卡，开启 `farm.aftermath` 擦屁股系列。
- `civil.captives` 转化成功后，减少俘虏危机卡，开启 `civil.naturalized` 归化民组织系列。
- `security.guard` 授权过高后，开启 `security.militarization` 军务化反噬系列。
- `planning.committee` 计划债务过高后，开启 `planning.debt_crisis` 问责系列。

### 10.6.2 第一版 MVP 系列

第一版先做 8 条核心系列，覆盖接触、生产、组织、军务、计划、市场和内部政治。

| 系列 id | 名称 | 主要解锁条件 | 主要作用 |
| --- | --- | --- | --- |
| `external.locals` | 本地接触 | 登陆后侦察或遭遇本地人 | 解锁本地村社、风声、农庄、贸易 |
| `farm.nanhai` | 南海农庄 | `external.locals` 达成接触 | 农业、生计、归化民安置、农庄坐大 |
| `civil.captives` | 俘虏治理 | 首批俘虏出现 | 民政、分化、释放、转化和反噬 |
| `civil.labor` | 劳工制度 | 俘虏/归化民规模扩大 | 工分、分层、待遇、基层秩序 |
| `security.guard` | 保卫授权 | 外部袭击或内部治安压力 | 军务、戒严、警戒和高压反噬 |
| `planning.committee` | 计划委员会 | 建设项目增多或马千瞩执政 | 工业、资源调度、计划债务 |
| `trade.dongmen` | 东门市 | 本地接触和物资交换增加 | 商贸、市场、治安、泄密 |
| `politics.council` | 元老会议 | 开局存在 | 会议、合法性、继任、架空和问责 |

这 8 条系列不需要全部一开始激活。开局主要有 `politics.council` 和少量登陆核心卡；其他系列随状态逐步进入候选池。

### 10.6.3 抽卡算法

新版抽卡不直接从全卡池随机抽，而是先处理强制事件，再按系列筛选和加权。

推荐流程：

1. 检查是否存在整局失败、人物倒台、继任、致命危机等强制事件。
2. 如果有未处理的 `pending` 插入卡，优先展示插入卡。
3. 收集所有系列定义，过滤不满足 `requires` 或命中 `excludes` 的系列。
4. 根据当前人物、阶段、状态、隐藏势力和前任遗产调整系列权重。
5. 按权重先抽取一个系列。
6. 在该系列内过滤可用卡牌，排除条件不满足、已关闭、近期重复或已永久使用的卡。
7. 按卡牌权重抽取具体卡牌。
8. 应用变体：前任遗产/擦屁股、当前人物、势力状态、阶段和历史状态。
9. 生成最终正文、来源、左右选项和提示。
10. 玩家选择后结算四柱、风声、隐藏势力、人物压力、状态变化、天数和后续卡。

优先级仍保留，但它作用在“强制事件”和“系列内卡牌类型”两个层面：

| 优先级 | 类型 |
| ---: | --- |
| 1 | 整局失败、人物倒台、继任 |
| 2 | 未处理插入卡 |
| 3 | 致命危机 |
| 4 | 人物反噬 |
| 5 | 势力索价 |
| 6 | 系列关键节点 |
| 7 | 人物专属卡 |
| 8 | 公用日常卡 |

系列权重可以被多种因素修正：

- 当前人物标签命中系列标签时，系列权重上升。
- 某隐藏势力影响力过高时，该势力相关系列权重上升。
- 某势力满意度过低或敌意过高时，危机、索价、反噬卡权重上升。
- 某系列进度长期停滞时，推进卡权重上升。
- 前任留下烂账时，擦屁股系列和遗产变体权重上升。
- 近期连续出现同一系列时，该系列短期降权，避免事件过度重复。

伪代码：

```js
function drawNextCard(state, content) {
  const forced = findForcedEvent(state, content);
  if (forced) return forced;

  const pending = drawPendingCard(state, content);
  if (pending) return pending;

  const availableSeries = content.series
    .filter((series) => matchConditions(series.requires, state))
    .filter((series) => !matchConditions(series.excludes, state))
    .map((series) => applySeriesWeight(series, state));

  const series = weightedPick(availableSeries);
  const cards = content.cards
    .filter((card) => card.series === series.id)
    .filter((card) => matchConditions(card.requires, state))
    .filter((card) => !matchConditions(card.excludes, state))
    .map((card) => applyCardWeight(card, state));

  const card = weightedPick(cards);
  return applyBestVariants(card, state);
}
```

第一版实现时，不需要一次做完所有加权因素，但数据结构必须预留这些入口。

### 10.7 数据存储格式

卡牌不应设计成“数据库字段”。一张卡应该是一条结构化记录，包含 id、主题池、类型、来源、标签、条件、左右选项、变体和后续事件。数据库只有在需要在线编辑器、多用户协作、玩家上传内容或运行期热更新时才有必要。

第一版推荐采用“内容包 JSON + 引擎加载器校验”：

- 作者维护 `game/content/official/` 下的官方 JSON 内容包；Mod 以后使用同样结构。
- 每张卡是一个对象，每个主题池一个或多个文件。
- 工具脚本校验字段、标签、引用、条件和数值范围。
- `game/src/engine/` 只读取加载器校验后的结构化数据，不直接写死官方内容。

不建议一开始上数据库，因为当前项目是静态网页游戏，数据库会明显增加复杂度。策划说明可以写在相邻 Markdown 文档里，JSON 文件只保存机器可校验的数据。

### 10.8 数据文件结构

推荐把内容包和引擎代码分开：内容放在 `game/content/`，运行时代码放在 `game/src/`，`web/` 以后只做平台壳。

```text
game/
  content/
    official/
      characters/
        core.json
      cards/
        core.json
      states/
        core.json
      series/
        core.json
  src/
    app/
    engine/
      character/
      state/

tools/
  validate_content.py
```

`game/content/` 是官方内容包源文件，`game/src/engine/` 是规则和加载逻辑。后续 Mod 内容包应复用同样目录和字段结构。

### 10.9 卡牌记录结构

每张卡是一条完整记录，不拆成数据库式扁平字段。建议字段如下：

| 字段 | 作用 |
| --- | --- |
| `id` | 全局唯一编号，如 `FARM-001` |
| `pool` | 所属主题池，如 `farm`、`security` |
| `series` | 所属系列，如 `farm.nanhai` |
| `type` | 卡牌类型：日常、关键、危机、索价、反噬、倒台、遗产 |
| `title` | 卡牌标题 |
| `source` | 提出事件的人物或组织 |
| `tags` | 匹配人物、势力、阶段和变体 |
| `requires` | 出现条件 |
| `excludes` | 剔除条件 |
| `weight` | 基础抽取权重 |
| `text` | 默认正文 |
| `options` | 默认左右选项 |
| `variants` | 人物、势力、阶段、历史变体 |
| `followups` | 结算后可能注入的后续卡或事件 |

### 10.10 选项结构

选项只保留左右二选一。人物专属内容替换其中一侧，而不是增加第三选项。

```json
{
  "id": "model_project",
  "label": "集中资源办样板",
  "hint": "见效更快，也更扎眼",
  "effects": {
    "stats": { "people": 8, "livelihood": 5, "military": -3, "council": -4 },

      "farm": { "influence": 5, "satisfaction": 6 },

      { "id": "farm.model_project", "op": "set", "value": true },
      { "id": "farm.autonomy_level", "op": "add", "value": 1 }
    ]
  },
  "followups": ["FARM-003"]
}
```

### 10.11 变体结构

变体用于覆盖正文、提示、权重或某一侧选项。第一版重点做 `replaceOption` 和 `extraHint`。

```json
{
  "id": "wunanhai_commune",
  "kind": "character",
  "when": {
    "ruler": "wunanhai",
    "chance": 0.65,
    "tagsAny": ["农业", "农庄", "民生"]

  "option": {

    "effects": {
      "stats": { "people": 9, "livelihood": 4, "council": -5 },
      "forces": {
        "farm": { "influence": 7, "satisfaction": 6 },
        "locals": { "satisfaction": 3 }
      },
      "personal": { "wunanhai_pressure": 4 },
      "days": 3,
      "states": [
        { "id": "farm.established", "op": "set", "value": true },
        { "id": "farm.wunanhai_commune", "op": "set", "value": true },
        { "id": "farm.autonomy_level", "op": "add", "value": 2 }
      ]
    },
    "followups": ["FARM-WNH-001"]
  }
}
```

### 10.12 条件结构

条件统一写成小对象，便于校验和扩展。

```json
{
  "requires": [
    { "state": "contact.locals", "equals": true },
    { "force": "farm", "metric": "influence", "gte": 10 }
  ],
  "excludes": [
    { "state": "farm.destroyed", "equals": true },
    { "used": "FARM-001" }
  ]
}
```

第一版需要支持的条件类型：

- `state`：状态库中的世界状态、制度状态、项目状态或路线状态。
- `used`：某卡是否已出现。
- `ruler`：当前执政人物。
- `formerRuler`：前任人物。
- `force`：隐藏势力数值。
- `stat`：四柱指标。
- `wind`：风声。
- `stage`：当前阶段。
- `day`：天数范围。

### 10.13 状态库

状态库用于维护“世界已经变成什么样”。某些选择会导致状态变化，某些卡只有在满足指定状态时才会进入候选池。

状态库不是四柱，也不是隐藏势力数值：

- 四柱回答整体局势是否健康。
- 隐藏势力数值回答谁变强、谁满意、谁警惕。
- 状态库回答发生过什么、制度是什么版本、项目推进到哪一步。

状态定义放在 `game/content/official/states/core.json`。每个状态必须有唯一 id、类型、默认值和可见性。

```json
{
  "id": "farm.established",
  "name": "南海农庄已建立",
  "type": "boolean",
  "default": false,
  "visibility": "hidden",
  "mutability": "immutable",
  "tags": ["农庄", "农业", "本地人"],
  "desc": "解锁南海农庄后续卡池。"
}
```

第一版状态类型：

| 类型 | 用途 | 示例 |
| --- | --- | --- |
| `boolean` | 是否发生、是否建立 | `contact.locals`、`farm.established` |
| `counter` | 累计程度 | `security.militarization`、`planning.debt` |
| `level` | 等级或阶段 | `trade.market_level`、`farm.autonomy_level` |
| `enum` | 路线选择 | `labor.policy = soft / strict / militarized` |
| `timer` | 若干天后失效的临时状态 | `mourning.active` |
| `set` | 收集型状态 | `known_forces`、`former_rulers` |

状态变化写在选项效果中：

```json
{
  "effects": {
    "states": [
      { "id": "contact.locals", "op": "set", "value": true },
      { "id": "farm.autonomy_level", "op": "add", "value": 1 },
      { "id": "labor.policy", "op": "set", "value": "strict" },
      { "id": "known_forces", "op": "addToSet", "value": "locals" }
    ]
  }
}
```

状态可用于卡牌出现条件：

```json
{
  "requires": [
    { "state": "farm.established", "equals": true },
    { "state": "farm.autonomy_level", "gte": 2 }
  ],
  "excludes": [
    { "state": "farm.destroyed", "equals": true }
  ]
}
```

状态可见性分三档：

- `hidden`：完全隐藏，只通过卡牌文本暗示。
- `hinted`：不显示具体值，但报告或卡牌会给趋势提示。
- `public`：可以在界面、日志或结算中明确显示。

第一版默认大多数状态隐藏；只有剧情节点、已建立机构、当前政策、当前执政者等少数状态可以公开或半公开。

状态还必须声明可变性：

| 可变性 | 用途 | 示例 |
| --- | --- | --- |
| `immutable` | 已发生的历史事实、首次接触、死亡、机构创立 | `contact.locals`、`first_death.occurred`、`farm.established` |
| `reversible` | 当前政策、等级、临时局势、项目状态 | `martial_law.active`、`trade.market_level`、`labor.policy` |
| `terminal` | 会关闭或终结某条线的后果状态 | `farm.destroyed`、`character.wunanhai.dead` |

`immutable` 和 `terminal` 状态可以从默认值推进到新值，但不能被普通卡牌改回。若剧情上必须推翻一个历史事实，应新增另一个状态表示后果，例如不用把 `farm.established` 改回 `false`，而是设置 `farm.destroyed = true` 或 `farm.seized = true`。

状态定义示例：

```json
[
  {
    "id": "contact.locals",
    "name": "已接触本地人",
    "type": "boolean",
    "default": false,
    "visibility": "hinted",
    "mutability": "immutable",
    "desc": "解锁本地村社、误会、贸易和归化相关卡。"
  },
  {
    "id": "labor.policy",
    "name": "当前劳工政策",
    "type": "enum",
    "values": ["unset", "soft", "strict", "militarized"],
    "default": "unset",
    "visibility": "public",
    "mutability": "reversible",
    "desc": "影响工分、俘虏、归化民和基层组织卡池。"
  }
]
```

## 11. Mod 支持

Mod 支持必须从第一版数据结构开始预留。官方内容也应视为一个内置内容包，而不是写死在程序里。

### 11.1 基本原则

- Mod 是数据包，默认不执行任意 JavaScript 代码。
- Mod 可以新增或覆盖人物、势力、状态、系列、卡牌、文本和结局。
- Mod 通过命名空间隔离 id，避免和官方内容冲突。
- 引擎只读取标准 schema，所有内容包先校验再加载。
- 存档记录启用的 Mod 列表和版本，避免读档时内容缺失。

### 11.2 内容包结构

```text
mods/
  example-mod/
    mod.json
    characters.json
    forces.json
    states.json
    series.json
    cards/
      farm.json
      politics.json
    assets/
      portraits/
```

`mod.json` 示例：

```json
{
  "id": "example.new-faction",
  "name": "新派系示例",
  "version": "0.1.0",
  "gameVersion": "0.2.x",
  "author": "player",
  "priority": 100,
  "dependencies": [],
  "entry": {
    "characters": "characters.json",
    "forces": "forces.json",
```

### 11.3 加载与覆盖规则

内容加载顺序：

1. 官方核心包。
2. 官方扩展包。
3. 用户启用的 Mod，按依赖和优先级排序。

同 id 内容默认禁止重复定义。若 Mod 要覆盖官方内容，必须显式声明：

```json
{
  "op": "patch",
  "target": "FARM-001",
  "changes": {
    "weight": 5
  }
}
```

第一版只支持新增内容和简单 patch；不支持执行脚本型 Mod。

### 11.4 平台差异

Web/PWA 版可以支持导入本地 Mod 包，但浏览器文件权限有限，应优先支持“导入 zip 或 json 包并保存到本地存储”。

桌面版可通过 Tauri 读取本地 Mod 文件夹，适合高级 Mod 管理。

移动端可通过 Capacitor 文件系统或应用内导入包支持 Mod，但不应依赖玩家手动访问复杂目录。

### 11.5 与框架选择的关系

为了支持 Mod，前端不应依赖重型 UI 框架或把内容写进组件。推荐：

- 核心引擎使用 TypeScript 写成纯逻辑模块。
- UI 先用原生 HTML/CSS/TypeScript。
- 数据源采用 JSON 内容包，由加载器校验后进入运行时。
- 后续 Web/PWA、Tauri、Capacitor 共用同一套引擎和内容加载器。

## 12. 总失败与胜利

暂不设置明确胜利。游戏重点是长期执政、继任和局势演化。

总崩局可以包括：

- 元老院分裂
- 军务失控
- 民变或归化民反噬
- 外部围剿
- 生产崩溃
- 继任合法性崩溃

这些是整局结束条件，区别于单个人物下台。

## 13. 暂定与待定

已确认：

- 五名首发人物。
- 人物下台后游戏继续。
- 势力隐藏，不显示面板。
- 公用卡保留左右二选一，人物专属内容替换其中一个选项或提供额外提示。
- 势力通过事件解锁，旧卡可以退出，新卡可以加入。
- 不加入主动议程槽，第一版仍以卡牌推进为主。
- 预留 Mod 支持，官方内容也按内置内容包组织。

待继续确定：

- 每名人物的主动能力、缺陷、初始数值和专属标签。
- 隐藏势力的具体列表、解锁条件和收益索价。
- 倒台触发规则与总崩局阈值。
- 继任者候选池和自动推举公式。
- 第一版 MVP 卡牌数量。
- Mod 的导入格式、冲突处理 UI 和跨平台存储策略。
